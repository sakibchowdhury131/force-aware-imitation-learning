# Force-Sensing Calibration: Findings

Kinova Jaco2 (6-DOF), `pastaTransfer4` task. Covers two linked investigations:
(1) removing gravity error from joint torque so external force can be
recovered, and (2) whether the remaining mass/Coriolis dynamics residual is
better modeled by a physics regressor or a neural network.

Related artifacts (interactive, with charts):
- Gravity calibration report: https://claude.ai/code/artifact/aa299a1c-9d7e-4a37-95e7-26a097f2da03
- Mass/Coriolis regressor-vs-NN report: https://claude.ai/code/artifact/8d729f0b-ba1e-46bc-9753-a3585a2079e3

---

## 1. Background

The full joint-torque equation:

```
tau = M(q)*qddot + C(q,qdot)*qdot + G(q) + tau_friction + J^T(q)*F_tip
```

Recovering `F_tip` (external contact force) requires correctly modeling and
subtracting everything else. This document covers how `G(q)` (gravity) and
`M(q)*qddot + C(q,qdot)*qdot` (mass/Coriolis dynamics) were each calibrated,
in two layers: a firmware/physics layer first, then a residual-correction
layer on top.

## 2. Gravity calibration

### 2.1 Firmware gravity matrix (`calibrate_firmware_gravity.py`)

Kinova's own `RunGravityZEstimationSequence` + `SetGravityOptimalZParam`.

- **First attempt**: 93.8% reduction, but the fitted parameters destabilized
  actuator J6 (fault, joystick red lights, one-direction-only rotation until
  power cycle). Root cause suspected: uncalibrated torque sensors at the
  hardware level (undocumented precondition of this SDK routine). **Result
  discarded — do not reuse.**
- **Second attempt** (clean): mean ||F|| 21.41N -> 1.69N (**92.1% reduction**)
  across 8 calibration poses, confirmed fault-free on hardware.
  - Held-out check (6 new poses, same region): 1.81-1.87N — generalizes well
    *near* its own calibration poses.
  - Out-of-region check (pose with J2=111.7°, calibration spanned ~183-223°):
    degraded to 6.51N — real generalization gap outside the calibrated
    region.
- **Persistence**: firmware gravity params do NOT survive a power cycle
  (confirmed twice) — `apply_saved_gravity_params()` must be called once per
  session. This is now wired automatically into the startup of 8 scripts:
  `diag_contact.py`, `calibrate_contact_baseline.py`, `diag_joint_torques.py`,
  `replay_episode.py`, `07_deploy.py`, `teach_by_hand.py`,
  `quick_pose_check.py`, `test_residual_repeatability.py`.

### 2.2 Software gravity regressor — random poses (`calibrate_gravity_residual.py`)

Linear regressor `tau_residual(q) = Y_g(q) @ phi`, ridge-fit from poses
generated by perturbing around known-safe anchor configurations (no relation
to any specific task).

- 24 poses accumulated over 3 batches: mean ||F|| 6.08N -> 5.32N
  (**12.5% reduction**), but inconsistent — 6 of 24 poses got *worse* (up to
  -63%), and the reduction **declined** with more data across batches
  (27.4% -> 20.9% -> 12.5%). This pattern motivated moving to real task poses
  instead of generic random ones.

### 2.3 Software gravity regressor — task poses (`collect_task_poses.py`)

Same linear regressor, but poses taken directly from real `pastaTransfer4`
episode trajectories (the actual poses the deployed policy visits) instead of
random perturbations.

- **Mixed test** (24 random + 9 task poses, evaluated on the 9 task poses
  specifically): 5.94N -> 3.34N (**43.7% reduction**), all 9 improved,
  37-51% each, no outliers — a much cleaner result than the random-only fit.
- **Task-only training** (40 poses from 8 episodes, no random poses at all):
  6.56N -> 1.43N (**78.2% reduction**), stable across all 4 accumulating
  batches (79.7% -> 78.2%), every pose improved, no decline with more data
  (unlike the random-pose experiment).
- **Held-out validation** (15 poses from 5 *entirely different* episodes,
  never used in training): 5.99N -> 1.51N (**74.8% reduction**), all 15
  improved (59-89% each), landing at the expected ~1-2N noise floor given
  the workspace had nothing to contact.
- **Conclusion**: calibrating on real task poses is dramatically better and
  more consistent than generic randomized poses — the improvement is
  concentrated specifically in the region the poses cover, confirmed by the
  fact that the combined random+task fit, re-evaluated on the *original* 24
  random poses, still only reached ~15.7% there.

Saved: `data/gravity_phi_task_only.npy` (the trusted fit) and
`data/gravity_calibration_records_task_only.npz` (the 40 training poses).

### 2.4 Gravity-residual neural network (`fit_gravity_residual_nn.py`)

A small NN, `G_res(q)` — input `sin(q), cos(q)` only (pose, never velocity or
acceleration) — fit **on top of** the existing linear `gravity_phi_task_only.npy`,
using exclusively static/near-zero-velocity data.

- Re-fitting the *linear* model with more poses barely helped (near-static
  residual only dropped 0.81 -> 0.77 N·m) — the fixed 24-parameter linear
  functional form, not lack of data, was the bottleneck.
- The nonlinear NN did far better:
  - 65 static samples (40 dedicated poses + near-static stretches mined from
    6 already-collected motion episodes, no new hardware time): 1.53N ->
    0.49N (**68.2%** train), 1.93N -> 1.13N (**41.3%** held-out, 18 samples
    from 3 untouched episodes).
  - Scaled to 190 static samples (30 episodes): 1.50N -> 0.55N (**63.0%**
    train), 1.93N -> 1.36N (**29.3%** held-out — dip likely small-sample
    noise at n=18, not a concern).
- **Conclusion**: for gravity, a nonlinear pose-only correction recovers far
  more of the residual than the linear model can, regardless of how much
  data the linear model gets. Genuine, uncontested win for the NN approach.

Saved: `data/gravity_residual_nn.pt`.

## 3. Mass/Coriolis dynamics residual: regressor vs. neural network

### 3.1 Technical foundation

`contact_detector.py`'s original `rnea_no_gravity` parametrizes each link by
(mass, COM) separately, which makes `M(q)*qddot + C(q,qdot)*qdot` **bilinear**,
not linear, in those parameters. Fixed by reparametrizing to the standard
barycentric form:

- `mass` (1 param/link)
- `h = mass * COM` — first moment (3 params/link; same quantity gravity's
  regressor already uses)
- `J` — inertia about the link's own reference **origin**, not COM (6
  independent params/link)

This makes the whole equation **exactly linear** in 10 params/link (60 total)
plus a viscous+Coulomb friction term (2 params/joint, 12 total) — 72
parameters overall (`full_dynamics_regressor`). Verified to ~1e-16 against
the original formulation before fitting anything. Later optimized (~1.9x
speedup: forward kinematics computed once per sample and reused across the
72 unit-perturbation calls, instead of recomputed 72 times) with no change
to any result (re-verified to the same precision).

### 3.2 First attempt — confounded result

Excitation data (motion needs real q̇/q̈, unlike the deliberately slow
quasi-static replays used for clean contact-force reading elsewhere in this
project): `replay_episode.py --no_wait_convergence --speed_scale 0.5
--arm_trans_speed 0.08`, 6 training + 3 held-out `pastaTransfer4` episodes.

Target: `gravity-free torque - gravity_regressor(q)@phi - rnea_no_gravity(q,qdot,qddot)`.

| Method | Train reduction | Held-out reduction |
|---|---|---|
| Linear regressor (72 params) | 4.2% | 3.6% |
| Neural network (unconstrained) | 39.0% | 34.1% |

The NN looked like a huge win. **It wasn't.** A direct check — feeding the NN
real held-out poses with `qdot=qddot=0` substituted, where a genuine
`M(q)*qddot+C(q,qdot)*qdot` effect is mathematically required to be exactly
zero — showed the NN still output ~1.48N, almost as large as its entire
real-world correction. Confirmed independently: near-static samples
(|qdot|<5°/s) carried nearly as much residual (0.81 N·m) as fast samples
(1.10 N·m), meaning most of the "residual" wasn't dynamics-dependent at all.

**Root cause**: the NN's input included `q` directly with no constraint
forcing zero output at rest, so it was quietly patching leftover
pose-dependent gravity error (see §2) that the regressor is mathematically
*incapable* of touching (`Y_full(q,qdot,qddot)` is exactly zero whenever
`qdot=qddot=0`, by construction, verified in self-test). Not a fair
comparison.

### 3.3 The fix (two parts, both required)

1. **Data fix**: subtract the gravity-residual NN's correction (§2.4) from
   the target *before* either dynamics model sees it, so neither is being
   asked to explain pose-only leftover error as if it were dynamics.
2. **Architecture fix**: rebuilt the NN as two physically-shaped heads
   instead of one monolithic network:
   - `M_res(q)` — input `sin(q), cos(q)` only — outputs a symmetric 6x6
     matrix — contributes `M_res(q) @ qddot`
   - `C_res(q, qdot)` — input `sin(q), cos(q), qdot` — outputs a general 6x6
     matrix — contributes `C_res(q,qdot) @ qdot`

   Both outputs are multiplied by `qddot`/`qdot` respectively, so the
   combined prediction is **exactly zero whenever qdot=qddot=0, for any
   network weights** — the same hard constraint the regressor already had.
   Verified directly: `max|prediction| = 0.00e+00` at synthetic rest points.

### 3.4 Corrected comparison — 6 training episodes

| Method | Train reduction | Held-out reduction |
|---|---|---|
| Regressor | 5.0% | 4.7% |
| Constrained NN | 16.3% | 6.8% |

Baseline itself (before either dynamics model does anything) dropped from
2.11/2.22N to 1.61/1.71N train/held-out just from the gravity fix (~24%).
The constrained NN still edged out the regressor on held-out data, but its
train-to-held-out drop (16.3% -> 6.8%, more than half) signaled it was
partly memorizing the 6 specific training episodes.

### 3.5 Scaled up — 30 training episodes (final result)

Collected 24 more excitation episodes (30 training episodes total: every
`pastaTransfer4` episode with tracked data except the 3 held-out ones,
which stayed completely untouched throughout). Gravity-residual NN refit on
190 static samples (up from 65). Dynamics target and both models rebuilt
from scratch (37,671 training samples, up from 7,514).

| Method | Train reduction (6 ep.) | Held-out (6 ep.) | Train reduction (30 ep.) | Held-out (30 ep.) |
|---|---|---|---|---|
| Regressor | 5.0% | 4.7% | 4.9% | **5.2%** |
| Constrained NN | 16.3% | 6.8% | 9.1% | **5.3%** |

With 5x more training data, the NN's train-set number fell (16.3% -> 9.1%,
it can no longer memorize 6 episodes as easily) while its held-out number
barely moved (6.8% -> 5.3%). The train/held-out gap shrank from 9.5 points
to 3.8. **Regressor and NN are now within noise of each other on held-out
data** (5.2% vs 5.3% — matching to 3 decimal places in mean and std of the
raw evaluation).

**This convergence is the real finding**: the true recoverable
mass/Coriolis effect in this workspace is small (~5%), and both a
72-parameter linear model and a flexible constrained NN land on the same
number once given enough data to stop overfitting. The NN's earlier
apparent 34-39% advantage was almost entirely a data-scarcity/confound
artifact, not a genuine capability gap.

## 4. Bottom line

- **Gravity residual**: use the NN (`fit_gravity_residual_nn.py`). Real,
  substantial, uncontested improvement (63-68% train, 29-41% held-out) over
  the linear model, because the true residual there (kinematic/sensor
  calibration error, not rigid-body physics) has no reason to be linear in
  anything.
- **Mass/Coriolis residual**: use the regressor (`fit_dynamics_regressor.py`
  / `full_dynamics_regressor`). Statistically tied with the NN in achievable
  accuracy (~5% either way), but far simpler, numerically stable across
  every configuration tried, fully inspectable, and mathematically
  guaranteed to never predict an unphysical result — because
  `M(q)*qddot+C(q,qdot)*qdot` is *exactly* the linear structure the
  regressor already encodes; there's little nonlinear-in-q structure left
  for a network to find.
- **Layering that works, end to end**: firmware gravity matrix ->
  software gravity regressor (`gravity_phi_task_only.npy`) -> gravity
  residual NN (`gravity_residual_nn.pt`) -> nominal RNEA
  (`rnea_no_gravity`) -> mass/Coriolis regressor
  (`dynamics_residual_pi.npy`) -> remainder is `tau_ext`, mapped to an
  end-effector wrench via `torque_to_wrench`.
